O nível max é a proteção mais forte oferecida por este comando. Ele aumenta o trabalho de quem tenta ler o JavaScript, mas não torna um app instalado impossível de copiar.

01 / A pasta certa

Projeto do app, não computador inteiro.

O CLI do AIOSON é o programa que você digita no terminal. Ele pode estar instalado globalmente ou ser chamado por npx. Já o javascript-obfuscator é usado durante a publicação e precisa estar instalado dentro de cada app que você quer proteger.

No celular, deslize a tabela para os lados.

Onde cada ferramenta fica
FerramentaOnde instalarPor quê
AIOSON CLIGlobalmente, ou execute por npxÉ o comando que você usa.
javascript-obfuscatorEm cada projeto de appO AIOSON carrega a versão exata do node_modules do app.

Exemplo no PowerShell: substitua o caminho pela pasta real do seu app. No macOS ou Linux, use um caminho como ~/projetos/minha-loja.

PowerShell · exemplo de caminho 
cd C:\projetos\minha-loja
dir package.json, system.json
macOS ou Linux · exemplo de caminho 
cd ~/projetos/minha-loja
ls package.json system.json

Se os dois arquivos aparecem, você está na pasta certa. Se o projeto usa várias pastas, escolha a pasta do app que será publicado, não a pasta do código-fonte do AIOSON.

Ainda não tenho o comando aioson no terminal. O que instalo?

Você pode instalar somente o CLI no computador ou usar npx @jaimevalasek/aioson no lugar de aioson nos comandos deste guia:

CLI global · opcional
npm install --global @jaimevalasek/aioson

Isso é separado do javascript-obfuscator, que continua sendo instalado dentro do app. Para usar mudanças locais deste repositório antes do próximo release, execute seu bin/aioson.js com node.

02 / Antes de instalar

Seu app precisa saber compilar e iniciar.

Tenha Node.js e npm funcionando. No terminal aberto dentro do app, confira:

Conferir ferramentas 
node --version
npm --version

O package.json precisa ter scripts build e start. O build gera arquivos executáveis, como dist/server.js; o start inicia esses arquivos. Um exemplo de app Node que já compila TypeScript:

package.json · trecho ilustrativo 
{
  "scripts": {
    "build": "tsc",
    "start": "node dist/server.js"
  }
}

Use os scripts reais do seu app. Se ele já compila corretamente, não substitua o package.json inteiro pelo exemplo. Antes de pensar na publicação, rode npm run build e confirme que o arquivo chamado por start foi gerado.

App com TypeScript executado diretamente?

Se o start usa tsx server/server.ts ou o Vite lê vite.config.ts, o AIOSON precisa de uma versão do Node com module.stripTypeScriptTypes e modo transform para proteger esses arquivos. A série Node 22 a partir da versão 22.13 e a série 24 oferecem esse recurso; o diagnóstico abaixo confirma se ele funciona no seu ambiente.

03 / Instalação

Instale a ofuscação no app.

Execute dentro da pasta do app:

Instalação local · PowerShell, macOS ou Linux 
npm install --save-dev --save-exact --ignore-scripts javascript-obfuscator
  • --save-dev registra a ferramenta para preparar a publicação; ela não precisa ser um arquivo do app distribuído.
  • --save-exact grava uma versão fixa no package.json. O nível max exige essa versão exata.
  • --ignore-scripts evita executar scripts de instalação de dependências nesse comando.

Você não precisa instalar o Terser separadamente: o AIOSON já o usa no nível standard e antes da ofuscação max.

Confira se ela ficou no projeto:

Verificar a instalação 
npm ls javascript-obfuscator --depth=0

O comando deve mostrar a versão instalada. Depois, abra o package.json e confira que a versão foi gravada sem ^ ou ~. Guarde as mudanças em package.json e package-lock.json com o seu projeto; não copie node_modules para o ZIP.

04 / Configuração

Peça o nível máximo ao AIOSON.

Na raiz do app, o system.json identifica o pacote. Sem configuração extra, --build usa standard (minificação). Este exemplo escolhe max como padrão do app:

system.json · exemplo 
{
  "slug": "minha-loja",
  "name": "Minha Loja",
  "version": "1.0.0",
  "build_command": "npm run build",
  "build_protection": "max"
}

Troque slug e name pelos dados do seu app. O build_command usa o script build do package.json. Se seu build grava em uma pasta diferente de dist/, build/, out/ ou .next/, acrescente, por exemplo, "build_output_dirs": ["dist-server"] ao JSON.

Exemplo completo para saída em dist-server 
{
  "slug": "minha-loja",
  "name": "Minha Loja",
  "version": "1.0.0",
  "build_command": "npm run build",
  "build_protection": "max",
  "build_output_dirs": ["dist-server"]
}

Use essa opção apenas se o seu build realmente criar dist-server/.

O que significa max?

O AIOSON minifica o JS com Terser e usa o javascript-obfuscator para embaralhar nomes, strings e fluxo de execução. É o nível mais forte deste comando, não um serviço de criptografia nem o produto Pro/VM da biblioteca. O resultado pode ficar maior ou mais lento; teste o app instalado.

05 / Conferir sem enviar

Faça o ensaio antes da publicação.

  1. Gere o build.

    O diagnóstico também roda o build, mas executar este passo separado ajuda a reconhecer erros do próprio app.

    Na pasta do app
    npm run build
  2. Rode o diagnóstico do pacote protegido.

    Ele lista os caminhos coletados, informa o nível de proteção e sai com erro se a proteção, a coleta ou o start falhar. Não exige login nem envia o ZIP; pode atualizar a saída local do build.

    Não publica
    aioson system:publish . --build --protection=max --dry-run
  3. Leia a lista.

    Confirme que a saída compilada aparece e que src/, testes e arquivos .map ficaram fora. Recursos necessários em runtime, como package.json, vite.config.* e squads, podem aparecer. Corrija qualquer erro antes de publicar.

Se o comando aioson não estiver instalado no computador, use npx @jaimevalasek/aioson no lugar de aioson. Para testar alterações deste repositório antes de uma versão nova chegar ao npm, chame o bin/aioson.js da sua cópia local do AIOSON com node. O ensaio ainda não verifica o tamanho final do ZIP.

Mesmo diagnóstico, sem instalar o CLI globalmente
npx @jaimevalasek/aioson system:publish . --build --protection=max --dry-run

06 / Publicação

Depois do ensaio, publique.

A publicação real exige login na sua conta AIOSON. Estes comandos enviam o pacote; execute-os somente quando estiver pronto para disponibilizar o app.

Entrar na conta 
aioson auth:login
Publicar como privado primeiro 
aioson system:publish . --build --protection=max --private

Instale e abra essa versão no AIOSON Play para conferir as telas, rotas e funções principais. O npm start na sua pasta testa o build local, mas não substitui esse teste: a ofuscação é aplicada ao pacote durante a publicação.

Para publicar com visibilidade pública, retire --private:

Publicação pública 
aioson system:publish . --build --protection=max

A primeira publicação pública de uma conta nova pode ficar em rascunho na Store até ser liberada; leia a mensagem final do terminal para saber o estado do seu app.

Não use --allow-raw-source para resolver erros.

Essa opção autoriza enviar código que não pôde ser protegido. Descubra o arquivo indicado, corrija o build e repita o diagnóstico.

07 / Segurança real

O que fica protegido e o que continua visível?

No celular, deslize a tabela para os lados.

Conteúdo típico de um pacote com --build --protection=max
ConteúdoO que acontece
src/ e mapas .mapFicam fora do pacote.
JS/JSX incluídoPassa por minificação e ofuscação; o envio falha se a transformação não funcionar.
TypeScript executado em runtime e vite.config.tsPassa por remoção de tipos e proteção quando o Node suporta a transformação; caso contrário, o envio falha.
JSON, HTML, CSS, imagens e prompts de squadsContinuam legíveis quando o app precisa deles em runtime. Scripts embutidos no HTML também continuam legíveis.
ZIP recebido pelo instaladorÉ extraído no computador de quem instala. Quem tem acesso pode copiar os arquivos.

Ofuscação aumenta o esforço de leitura; não impede cópia. Regras, prompts ou segredos que ninguém pode receber devem ficar em um serviço seu, acessado pelo app, e não no ZIP. O AIOSON bloqueia alguns segredos reconhecidos, mas isso não substitui revisar a lista de arquivos.

08 / Diagnóstico

Se aparecer um erro, siga o arquivo citado.

No celular, deslize a tabela para os lados.

Correções mais comuns
Mensagem ou sintomaO que fazer
Ofuscador ausenteVolte à pasta do app e rode a instalação local. Confira se node_modules/javascript-obfuscator está nessa pasta; uma instalação global ou em uma pasta-pai não serve.
Versão não fixadaReinstale com --save-exact. No package.json, a versão deve aparecer sem ^ ou ~.
Arquivo JS/JSX não protegidoCompile JSX para JS no build e corrija a sintaxe do arquivo citado. Repita o --dry-run.
TypeScript de runtime legívelUse um Node compatível com a transformação de TypeScript ou compile esse arquivo no build.
start ausente ou aponta para arquivo que não viajouCorrija o script start e, se necessário, declare build_output_dirs no system.json.
Segredo reconhecidoRemova a credencial do arquivo. Guarde segredos no servidor ou na configuração por instalação, nunca no pacote.
App instalado ficou lento ou falhouTeste rotas e funções no Play, reduza o bundle ou escolha conscientemente standard. Esse nível minifica, mas não aplica a ofuscação extra.
