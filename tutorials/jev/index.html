Este tutorial ensina o runner genérico. Consumidores especializados podem reutilizá-lo sem duplicar a chamada à API.

01 / Conceito

Jev não escreve o site. Ele responde perguntas que o software consegue usar.

Jev é um modelo System One: recebe um estado textual ou estruturado, avalia perguntas delimitadas e devolve valores tipados com probabilidades. Ele não conversa, não gera copy, não escreve HTML/CSS e não substitui Codex, Claude Code, Cursor ou outro modelo generativo.

Modelo generativo

Cria possibilidades

Escreve código, texto e componentes; usa ferramentas; interpreta pedidos abertos.

Jev

Julga possibilidades

Classifica, escolhe, pontua e verifica estados dentro de respostas conhecidas.

Código AIOSON

Aplica a política

Compara thresholds, ordena resultados, executa ações e mantém regras exatas.

Regra de ouro: se o código consegue calcular exatamente, calcule em código. Use Jev quando a decisão exige entendimento semântico — por exemplo, “esta direção parece específica para o domínio ou genérica?”.

02 / Arquitetura

Um runner central, muitos consumidores.

O comando jev:judge separa três responsabilidades. A configuração resolve rota e credencial; o cliente conversa com TypeSafe/OpenRouter; o julgamento valida a resposta e aplica a política. Notícias, design, QA e agentes podem reutilizar esse núcleo.

  1. 01Arquivo JSONstate + questions + decision
  2. 02Validação localestrutura, tipos, limites e referências
  3. 03Jevrespostas tipadas e probabilísticas
  4. 04Política em códigogate, seleção, ranking ou observação
  5. 05Consumidoraceitar, refinar, rotear ou revisar

A API key nunca entra no arquivo de julgamento. Isso permite versionar rubricas e fixtures sem versionar credenciais.

03 / Configuração

Escolha uma rota e habilite o Jev na raiz do projeto.

O AIOSON lê somente aioson-models.json na raiz. Use uma das rotas abaixo. O arquivo deve permanecer ignorado pelo Git.

Boa escolha para começar: usa a mesma conta OpenRouter que outros modelos e o endpoint Decisions.

{
  "providers": {
    "openrouter": {
      "api_key": "YOUR_OPENROUTER_API_KEY"
    }
  },
  "jev": {
    "enabled": true,
    "route": "openrouter",
    "model": "typesafe/jev-1.13",
    "min_noul": 0.6
  }
}

Alternativa por ambiente: $env:OPENROUTER_API_KEY = "...". A variável tem precedência sobre o arquivo.

Rota oficial direta: use uma chave TypeSafe e o endpoint /v1/systemone.

{
  "providers": {
    "typesafe": {
      "api_key": "YOUR_TYPESAFE_API_KEY"
    }
  },
  "jev": {
    "enabled": true,
    "route": "typesafe",
    "model": "jev-1.13.0",
    "min_noul": 0.6
  }
}

Alternativa por ambiente: $env:TYPESAFE_API_KEY = "...". A variável tem precedência sobre o arquivo.

Nunca faça commit da chave.O template traz placeholders; substitua apenas no arquivo local ou prefira a variável de ambiente.

04 / Primeiro uso

Gere um contrato, valide sem gastar e só então chame a API.

  1. Veja os exemplos.
    aioson jev:judge . --example=all --json
  2. Gere um gate editável.
    aioson jev:judge . --example=gate --out=.aioson/context/meu-julgamento.json
  3. Faça o dry-run.
    aioson jev:judge . --file=.aioson/context/meu-julgamento.json --dry-run --json

    Nenhum dado é enviado. O retorno mostra tamanho, rota, modelo, estado da configuração e o payload sem credencial.

  4. Execute e preserve a evidência.
    aioson jev:judge . --file=.aioson/context/meu-julgamento.json \
  --out=.aioson/context/meu-julgamento.result.json --json

05 / Contrato

O JSON descreve os fatos, as perguntas e o que fazer com as respostas.

{
  "version": 1,
  "id": "triagem-de-interface",
  "state": {
    "request": "Criar três direções visuais realmente diferentes",
    "surface": "landing page"
  },
  "questions": {
    "route": {
      "type": "choice",
      "instructions": "Qual rota atende melhor `request`?",
      "criteria": {
        "dev": "Implementação técnica já especificada",
        "ux_ui": "Uma decisão visual delimitada",
        "exploration": "Comparar múltiplas direções"
      }
    }
  },
  "decision": {
    "type": "select",
    "question": "route",
    "min_confidence": 0.55,
    "min_probability": 0.55,
    "on_uncertain": "human_review"
  }
}
state
Somente os dados necessários para o julgamento. Pode ser texto, objeto ou array.
questions
Mapa de perguntas independentes. O id é usado pelo código; o significado precisa estar nas instruções.
decision
Política determinística executada depois da resposta. Quando omitida, equivale a raw.

06 / Perguntas

Escolha o tipo pelo significado da resposta.

TipoPerguntaRespostaExemplo
noulUma condição é verdadeira?Probabilidade de 0 a 1“O resultado parece um template genérico?”
choiceQual opção delimitada vence?Opção, probabilidades e confiança“Rota DEV, UX/UI ou exploração?”
scoreEm qual nível ordenado o estado cai?Score contínuo, distribuição e confiança“Que nível de craft esta superfície atingiu?”

Perguntas enviadas juntas são avaliadas em paralelo. Elas não enxergam a resposta umas das outras; por isso cada instrução precisa apontar diretamente para os campos do estado que utiliza.

07 / Decisões

Quatro modos cobrem observação, portão, roteamento e comparação.

raw

Entregar respostas

Não escolhe por você. Serve quando outro módulo precisa compor pesos, guardar features ou aplicar uma regra própria.

"decision": { "type": "raw" }
gate

Aprovar ou devolver

Combina regras com all ou any. Pode ler resposta, confiança ou probabilidade de uma opção.

on_pass / on_fail
select

Escolher uma rota

Usa uma pergunta choice e exige confiança e probabilidade mínimas antes de aceitar a seleção.

on_uncertain
rank

Ordenar candidatos

Ordena perguntas independentes por score, noul ou confidence.

asc / desc

Operadores do gate

eq, neq, gt, gte, lt, lte, in e not_in. Para distribuições, use metric: "probability" e informe option.

09 / Design premium

Use Jev como diretor e júri; mantenha um modelo generativo como designer.

Briefingintenção + identidade + anti-referências
AIOSONdesign:seed + candidatos delimitados
Jevseleciona direção e riscos
LLMgera HTML, CSS e componentes
Browsermede DOM, pixels, craft e estados
Jev + códigoaceitar · refinar · regenerar · revisar

O estado do gate visual deve reunir evidência observável: design-seed.json, origem da paleta, fingerprint, craft.precision, alertas do verificador, métricas do navegador e uma descrição visual produzida por um modelo com visão.

Jev não recebe screenshots.A versão atual aceita texto/JSON. Converta imagem em descrição e métricas antes do julgamento; nunca finja que Jev viu pixels que não recebeu.

Dimensões úteis: especificidade do domínio, coerência com a identidade, hierarquia, distinção, acabamento, adequação ao tipo de superfície e risco de aparência genérica. Métricas exatas — contraste, contagem, tamanhos, distâncias — continuam no código.

10 / Inspeção automática

O CLI transforma HTML, CSS, JavaScript e o navegador em evidência para o Jev.

jev:review é a ponte entre o projeto real e jev:judge. Ele encontra ou recebe a interface, mede fatos determinísticos, extrai padrões e constrói o julgamento correspondente ao perfil escolhido.

  1. 01DescobertaHTML, CSS, componentes e entrada
  2. 02Estáticotokens, semântica, estados e riscos
  3. 03Runtimelayout real, overflow e responsividade
  4. 04Jevcoerência, qualidade e adequação
  5. 05Políticaaceitar, refinar ou coletar evidência
# Inspecionar sem usar a API
aioson jev:review . --profile=premium --evidence-only --json

# Ver o payload e a configuração sem chamar Jev
aioson jev:review . --dir=src --profile=design-system --dry-run --json

# Combinar código-fonte derivado com a aplicação renderizada
aioson jev:review . --dir=src --url=http://localhost:5173 --runtime \
  --profile=qa --criteria=.aioson/context/prd-minha-feature.md \
  --out=.aioson/context/jev-review-qa.json --json

# Revisar um protótipo pertencente ao briefing
aioson jev:review . --slug=minha-feature --runtime --profile=prototype \
  --criteria=.aioson/briefings/minha-feature/briefings.md --json
PerfilFocoConsumidor
premiumDistinção, coerência e craftDesign e auditoria ad hoc
prototypeDireção específica, completude e qualidade de aprovaçãoRefiner
qaProntidão, estados, responsividade e entregaQA
design-systemTokens, tipografia, spacing e consistênciaDesign/Dev
accessibilityRisco de exclusão e evidência ausenteQA
code-qualityCoerência e manutenibilidade dos padrõesDev/QA
Privacidade por padrãoO código da interface vira medições derivadas. --include-source inclui trechos limitados e --criteria envia o contrato redigido ao provedor externo.

O resultado final combina dois sinais. deterministic.verdict vem das medições locais; semantic.decision vem do Jev. Para passed: true, ambos precisam passar. Portanto, o modelo não consegue encobrir um erro objetivo.

Perfis prontos para os agentes

jev:agent-review combina artefatos canônicos com resultados determinísticos e oferece uma rota advisory para Briefing, Refiner, Product, Sheldon, Planner, Dev, QA, Tester e Pentester. Falhas obrigatórias são verificadas em código: um parecer positivo do modelo não as apaga.

# Conferir exatamente o estado e as perguntas, sem API
aioson jev:agent-review . --agent=sheldon --feature=minha-feature \
  --phase=review --evidence-only --json

# Revisão de QA com resultado auditável
aioson jev:agent-review . --agent=qa --feature=minha-feature \
  --phase=review \
  --out=.aioson/context/features/minha-feature/jev/qa-review.json --json
Advisory por padrão: decision.passed apoia o agente, mas nunca aprova um gate, corrige uma falha determinística ou substitui testes, runtime e decisão humana. Se o provedor estiver indisponível, o resultado é skipped e o fluxo normal continua.

Na revisão normal, o arquivo salvo contém respostas tipadas, probabilidades, política, modelo e hashes de proveniência — não os trechos dos artefatos enviados. Use --require-pass somente depois de comparar o perfil com casos reais e definir uma política explícita.

Para um gate de CI calibrado, acrescente --require-pass. O código 2 indica que não há aprovação válida, inclusive quando a chamada falha ou só prepara evidência/dry-run. Erros de entrada podem retornar 1. Julgamentos por promessa ou AC podem usar referências com caminho, linhas e hash em .aioson/context/features/<slug>/jev/evidence.json; o protocolo instalado explica os limites e o consentimento para compartilhar fontes.

aioson jev:judge . --file=quality-gate.json --require-pass --json
if ($LASTEXITCODE -eq 2) { Write-Error "Julgamento pediu revisão" }

12 / Resultado

Separe sucesso técnico de decisão aprovada.

{
  "ok": true,
  "status": "used",
  "route": "openrouter",
  "model": "typesafe/jev-1.13-20260917",
  "answers": {
    "premium_fit": { "type": "noul", "noul": 0.68 }
  },
  "decision": {
    "type": "gate",
    "passed": false,
    "action": "refine",
    "evaluations": [
      { "question": "premium_fit", "actual": 0.68, "op": "gte", "expected": 0.75, "passed": false }
    ]
  },
  "usage": { "input_tokens": 476, "output_tokens": 70, "cost": 0.000019992 },
  "attempts": 1
}
  • ok: true significa que o runner e a resposta funcionaram; não significa que o gate passou.
  • decision.passed é o veredito do gate.
  • decision.action é uma etiqueta; o consumidor decide o efeito real.
  • model registra a versão efetiva, útil quando um alias muda.

13 / Segurança e limites

Probabilidade não é permissão.

  • Credencial: somente no arquivo local ignorado ou variável de ambiente. Erros e saídas são redigidos.
  • Dados: envie apenas campos necessários. Estado grande e irrelevante reduz precisão e aumenta custo.
  • Ações críticas: confirmação humana continua obrigatória para publicação, exclusão, dinheiro, credenciais ou mudança irreversível.
  • Adversarial: trate o estado como dado potencialmente hostil; escreva critérios explícitos e teste casos de injeção.
  • Matemática: contagem, comparação numérica, datas e pesos ficam em código.
  • Calibração: thresholds de exemplos são pontos de partida, não verdades universais. Meça no domínio real.

O runner limita o arquivo a 512 KiB e aceita até 255 perguntas. choice aceita de 2 a 255 opções; score, de 2 a 10 níveis. Em falhas transitórias, tenta novamente apenas para 429, 502, 503, 524 e 529.

14 / Diagnóstico

Quando não funcionar, descubra em qual camada parou.

missing_api_key ou configuração desabilitada

Confirme jev.enabled: true, a rota e a chave correspondente. Rode --dry-run --json e leia config_status, route e model.

invalid_spec

Leia errors[]. O runner aponta o caminho exato: pergunta desconhecida, operador incompatível, opção inexistente ou threshold fora de 0–1.

invalid_response

A API respondeu, mas não cumpriu o contrato esperado. Preserve a saída, o modelo efetivo e o id da requisição; não aplique a decisão.

429 ou 529

O cliente usa backoff e respeita retry-after. Ajuste --retries=0..4 e --timeout=1000..120000 conforme o consumidor.

Resultados literais ou inconsistentes

Reduza o estado, elimine indireções, divida julgamentos compostos e torne critérios positivos/negativos explícitos. Não esconda várias decisões numa pergunta.

15 / Referência rápida

Comandos para guardar.

# Exemplos
aioson jev:judge . --example=raw|gate|select|rank|all --json

# Validar sem API
aioson jev:judge . --file=julgamento.json --dry-run --json

# Executar e persistir resultado
aioson jev:judge . --file=julgamento.json --out=resultado.json --json

# Usar como gate de automação
aioson jev:judge . --file=julgamento.json --require-pass --json

# Ajustar resiliência
aioson jev:judge . --file=julgamento.json --timeout=45000 --retries=2 --json

# Coletar padrões sem API
aioson jev:review . --profile=premium --evidence-only --json

# Revisar fonte + aplicação renderizada
aioson jev:review . --dir=src --url=http://localhost:5173 --runtime --profile=qa --json

# Revisar semanticamente o handoff de um agente
aioson jev:agent-review . --agent=dev --feature=minha-feature --phase=handoff --json
